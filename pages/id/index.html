Pearl ID

Sign-in with Pearl — your key is your account. Sign a site's challenge, prove you hold the key, log in as your prl1… address. No passwords. No OAuth.

Honest limits

  • A signature proves control of a key — not a real-world identity, not trustworthiness, not humanity.
  • A credential replays until it expires. Relying parties must use single-use ≥128-bit challenges and short expiries — the math can't enforce that for them.
  • Read the domain line before you sign. Signing moves no PRL and broadcasts nothing, but never sign a challenge from a site you don't trust.
  • Keys live in this page's memory only. Wipe them when you're done on a shared machine.

Your identity key

Your Pearl ID is a BIP-86 key. Its identity is the tweaked keypath x-only pubkey — the same key that controls its PRL address. Sites see your prl1… address as your username.

Stays in this page's memory only. Never sent anywhere. Never written to disk by this page. Signing happens locally.

Relying-party integration

          
Add "Sign in with Pearl" to your site in an afternoon. The protocol is four steps; the verifier is twenty lines.

          
The protocol

          
    
            
  1. Issue: generate 32 random bytes (hex), store them server-side as single-use with a ≤5-minute TTL, and show the user your domain + the challenge.
    2. 
            
  2. Collect: the user returns a prl-id credential (this page's Sign-in tab produces one).
    3. 
            
  3. Verify: run the snippet below. It checks the signature, the address↔key binding, the domain, and the expiry.
    4. 
            
  4. Consume: check the credential's challenge equals the one you issued, then burn it — never accept the same challenge twice. The address field is the user's account id.

Security notes

          
    
            
  • Challenges MUST be ≥128-bit CSPRNG output, single-use, and bound to one domain. Reused challenges are replayable logins.
    • 
            
  • Keep credential lifetimes in minutes. A leaked credential is a bearer token until expires_at.
    • 
            
  • Always pass expectedDomain — a credential for another domain must not log anyone in here.
    • 
            
  • Signatures prove key control, not personhood. If you need humans, that's your problem to solve — the math won't.
    • 
            
  • Phishing: only ever sign challenges on the domain you intend to log in to. This page shows the domain big before signing for exactly that reason.
